# skip_file setting

## Overview

The netxms-doc-antora pipeline sends its Telegram notifications from `alpine/curl` command steps.
`notify-success` skips itself with `if [ -e .skip-deploy ]; then exit 0; fi` when the build step
decided not to deploy, because the site was already built from those commits.

Moving those steps to this plugin loses that line: a plugin step has no `commands`, and Woodpecker's
`when:` can't test for a file. A new `skip_file` setting puts the check inside the plugin. When the
file exists, the plugin logs a line and exits 0. It does this before the bot is created, so a
skipped run makes no Telegram call (`NewBotAPIWithOptions` calls `getMe`) and can't fail on
Telegram.

Fork only: no upstream PR to appleboy. The fork is kept anyway for the `CI_PIPELINE_STATUS` fix.

## Decisions

- **Placement:** right after the existing `token`/`to` presence check, before the message is loaded.
  A missing secret then fails every run the same way, instead of passing quietly whenever deploy is
  skipped.
- **Stat result:**
  - The file exists: skip.
  - `fs.ErrNotExist`: send as usual.
  - Any other error: return an error naming the path. When the plugin can't tell whether the
    marker exists (permissions, a symlink loop), it must not send the success message the marker
    is there to stop.
  - Use `os.Stat`, not `Lstat`, to match the existing `[ -e ]` check.
- **Marker:** only whether the file exists matters; its contents are ignored. A relative path
  resolves against the step's working directory. That is the workspace for Woodpecker plugin steps,
  and none of the doc pipeline's steps override it.
- **Flag:** `skip.file`, read from `PLUGIN_SKIP_FILE,TELEGRAM_SKIP_FILE,INPUT_SKIP_FILE` (the same
  aliases as `message.file`). It is a string flag, so it doesn't go in `unsetEmptyEnv`.
- **Ruled out:**
  - The empty-message-file trick in the doc repo's uncommitted local migration: it still calls
    `getMe`, and it makes the pipeline depend on a template file that the build step copies from
    `main`.
  - Staying on the curl steps: that works today. Moving to the plugin is the user's choice.

## Implementation Steps

### Task 1: skip_file setting

Touches: `main.go` (flag, `Config` wiring in `run`), `plugin.go` (`Exec`), `plugin_test.go`,
`main_test.go`, `DOCS.md`, `README.md`.

Tests:
- **App test:** run the unmodified `newApp()` with its real `Action`, after `clearCIEnv`. Set
  `PLUGIN_SKIP_FILE` to an existing temporary file, a dummy token and recipient, and
  `PLUGIN_MESSAGE_FILE` to a path that doesn't exist.
  - It must return nil. If parsing or the `Config` wiring in `run` breaks, the run reaches the
    message file and returns the "error loading message file" error instead.
  - A swapped-`Action` callback, the `TestNewAppWoodpeckerEnv` pattern, would bypass `run`, so it
    is not enough here.
- **`Exec` tests** (missing message file in each case):
  - When the marker is missing, `Exec` returns the message-file error. `TestRenderMessagesErrors`
    already runs `Exec` with a missing message file, so this case can extend it.
  - When the marker path has an embedded NUL, `Exec` returns the wrapped `Stat` error (`EINVAL`).
    ⚠️ This replaces the planned self-referential symlink, which can't be created by an ordinary
    Windows account. Windows is a release target, though CI tests run on ubuntu only.
- **Network:** none of the new tests reach Telegram. `make test` as a whole still makes the
  `getMe` attempt in `TestBotError`.

- [x] `skip_file` skips sending when the file exists, sends as usual when it doesn't, and fails on
      any other `Stat` error
- [x] tests for the marker-present, marker-missing and unexpected-`Stat` cases, as above
- [x] DOCS.md gets a Parameter Reference entry; the README gets an example of a skipped deploy not announcing
      success
- [x] `make test`, `make lint`, `make fmt-check` pass

### Task 3: netxms-doc-antora pipeline

This task is in the other repo, `~/Development/netxms/netxms-doc-antora`.

**Baseline:** the committed `build.yaml`, which is identical on `main`, `v6.2`, `v7.0`, `next-6.2`
and `next-7.0`. The working tree also holds an uncommitted migration to `appleboy/drone-telegram`:
`build.yaml`, a new `tools/ci-notify-success.txt` and a CLAUDE.md edit. That migration is not
published as an intermediate step. An old workflow running that YAML would fetch a newer `main`
and fail at the `cp` once the template is gone. The commit goes straight from the curl config to
the final one, so the template file never lands, and the user decides what happens to the local
changes.

**Final config:**
- Both notify steps use the fork's `X.Y.Z` image.
- Both steps send inline messages. `notify-success` also sets `skip_file: .skip-deploy`.
- The build step still writes `.skip-deploy`, which the deploy step also checks. Nothing else
  changes in the build step.
- `notify-failure` doesn't need `skip_file`. A failed build never leaves `.skip-deploy`, because
  the skip path ends with `exit 0`.
- The plugin's message format replaces the curl text. The failure step has to stay correct with
  the plugin's own status handling, so it keeps `when.status: failure`.

**Branches:** that repo's CLAUDE.md requires `.woodpecker/` to be identical on all branches.
- Commit on `main`, then apply the same `build.yaml` to `v6.2` and `v7.0`. Per `docs/releasing.md`
  this counts as a correction true at the current tag.
- The `next-X.Y` queues pick it up through the usual `git rebase vX.Y`. They don't trigger CI, but
  promotion is a fast-forward, so the rebase has to happen before the next promotion.
- `next-7.0` currently equals `v7.0`, so it fast-forwards. `next-6.2` carries 27 queue commits.
  Whether to rebase it now is the user's call; this change doesn't require it.
- CLAUDE.md is main-only process content.

**Before committing,** the user checks that Woodpecker's plugin filters on the
`telegram_bot_token` and `telegram_channel_id` secrets allow the fork image.

**Line re-wrap:** the working tree also has unstaged edits to `build.yaml` that only re-wrap the
`>-` scalars (the fetch, wget/cmp, ssh-keyscan and lftp lines). They would land on every branch
along with this change. The user decides whether they go in.
